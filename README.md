# Postix — MVP социальной публикации (лента + лонгрид-редактор)

Postix — это MVP-приложение для публикации постов в стиле «лента первым» и отдельного полноценного редактора лонгридов. Визуальный язык — «blueprint»: единая палитра действий (blue/green/red) и единообразная обработка hover.

**Стек:** Rust (workspace), Yew + WebAssembly (client), Actix Web (server), PostgreSQL + Redis, DDD на бэкенде, FSD на фронтенде.

---

## 🚀 Быстрый старт

1. Скопируй `.env.example` в `.env`:

```bash
cp .env.example .env
```

2. Подними зависимости (PostgreSQL, Redis):

```bash
docker compose up -d postgres redis
```

3. Запусти сервер:

```bash
cargo run -p server
```

4. Запусти клиент:

```bash
cd client && trunk serve
```
Клиент будет доступен по адресу http://localhost:8080.

## Сборка клиента (production)

```bash
cd client && trunk build --release
```

## Проверки и тесты

```bash
cargo fmt --all -- --check
cargo test --workspace

```

## 🗂 Структура workspace

- client/ | Yew SPA на WebAssembly.
- server/ | Actix Web API, персистентность, миграции.
- core/   | Независимый крейт контрактов (типы запросов/ответов), общий для client и server.

## 🏗 Архитектура

### Сервер: DDD
Слои с зависимостями внутрь:

- server/src/domain/ | сущности, доменные правила, интерфейсы репозиториев. Без SQL, HTTP и фреймворк-деталей.
- server/src/application/ | use cases, оркестрация через доменные интерфейсы. Здесь валидируются доменные лимиты (пост ≤ 30 000 символов, отзыв ≤ 10 000, жалоба ≤ 3 000; один отзыв на пользователя на пост; оценка 1–5).
- server/src/infrastructure/ | адаптеры PostgreSQL/Redis, миграции, auth-middleware, реализации безопасности. Здесь же schema.dbml — единый источник правды по схеме БД.
- server/src/presentation/ | роуты, хэндлеры, экстракторы, маппинг DTO, преобразование ошибок в HTTP.
- server/migrations/ | forward-only миграции. Никогда не редактируйте уже применённые миграции.

__Границы__: не обходите application-сервисы из хэндлеров; не обращайтесь к инфраструктурным репозиториям напрямую из domain.

### Клиент: FSD

- client/src/app/ — настройка приложения, роутер, layout.
- client/src/pages/ — композиция на уровне роутов (без бизнес-логики).
- client/src/widgets/ — крупные переиспользуемые секции (лента, хедер).
- client/src/features/ — действия и потоки пользователя (аутентификация, создание поста).
- client/src/entities/ — модели (пост, пользователь), доступ к API.
- client/src/shared/ — общие UI-примитивы.

__Правила импортов__: однонаправленные импорты сверху вниз; `shared` не зависит от `features/widgets/pages;` публичные API слайсов — через `mod.rs`.

## ✨ MVP-функциональность

### Основной UX
- __Лента__ (`Home /`) | главный экран. Показывает карточки-превью: заголовок + первые 200 символов тела, метаданные (просмотры, рейтинг, время, автор, аватар), быстрые действия (закладки, жалоба). Клик ведёт на `/posts/:uuid`.
- __Отдельный редактор__ | создание и редактирование поста только на отдельных страницах (`/posts/create`, `/posts/:uuid/edit`). Редактор не появляется на ленте.
- __Пост__ | plain text (без Markdown/HTML), лимиты: заголовок + тело ≤ 30 000 символов. Поддерживает хэштеги, оценку 1–5, отзывы.
- __Отзыв__ | один на пользователя на пост, редактируемый, плоский (без тредов), до 10 000 символов. Другие пользователи могут ставить Agree/Dislike (отдельно от оценки поста).
- __Жалобы__ | до 3 000 символов.
- __Закладки__ | определяют "заинтересованность" для уведомлений.
- __Черновики и мягко удалённые посты__ | приватные, не попадают в публичную ленту.

### Поиск и профиль
- __Поиск__ (`/search`) — фильтры по времени, популярности, контенту, заголовку; префиксные операторы @name (автор), #tag (хэштег).
- __Профиль__ (`/profile`) — данные пользователя, статистика, табы Published/Draft (как ленты), редактирование профиля и выход из аккаунта (только здесь).

### Авторизация
- /auth/sign-up, /auth/sign-in — email/password.
- Неаутентифицированные пользователи видят только About, sign-in, sign-up.
- Сервер не хранит состояние сессии; при невалидном токене — 401. Клиент обновляет access token при старте и один раз повторяет запрос после 401. При ошибке refresh — очистка состояния и редирект на sign-in.

## 🔐 Безопасность и валидация

- Весь клиентский ввод считается недоверенным. Тело поста рендерится как текст, без raw HTML.
- Доменные лимиты и правила валидируются в `domain/application`, не только в UI.
- Токены, пароли и другие секреты не логируются. Секреты — в `.env`.
- История изменений фиксируется в БД; уведомления — только после реализации end-to-end потока

## 📦 Схема данных и миграции

- Единый источник правды по схеме — `server/src/infrastructure/schema.dbml`.
- Каждое изменение БД — forward-only миграция + обновление schema.dbml в том же коммите.
- Если ты работал над схемами уведомлений (rating/review) или социальной сети — эти наработки учитываются в рамках MVP-границ: реализуем только то, что явно нужно для текущего скоупа и контрактов API.

## 🧪 Тестирование

- __Unit-тесты__ | для новых доменных правил, трансформаций и валидации.
- __Integration-тесты (Actix)__ | для нового/изменённого поведения API, включая контракты ответов и аутентификацию. Тесты с БД должны использовать изолированную схему/БД и не зависеть от общей dev-базы.
- __Клиентские тесты__ | роутинг, контракты API, поведение состояния/refresh.
- Тесты должны быть детерминированными. Избегайте требования живого PostgreSQL/Redis, если это не environment-backed integration-тест.

Перед коммитом запускай:

```bash
cargo fmt --all -- --check
cargo test --workspace
```

## 🤝 Как вносить изменения

- Делайте небольшие, сфокусированные изменения, следуя паттернам Rust/Yew.
- Новые эндпоинты добавляйте только если MVP явно этого требует.
- Обновляйте `AGENT.md` и `README.md`, если существенно меняются архитектура, MVP-поведение или команды проекта.

## ❓ Частые вопросы

__Q: Где искать контракты API?__
A: В крейте core/ (типы запросов и ответов).

__Q: Как правильно менять схему БД?__
A: Только через forward-only миграцию + обновление server/src/infrastructure/schema.dbml. Не редактируйте старые миграции.

__Q: Что из «социального» уже есть в MVP?__
A: Посты, оценки 1–5, плоские отзывы (один на пользователя на пост), реакции на отзывы (Agree/Disagree), закладки, жалобы, поиск с префиксами. Подписки, треды, алгоритмический ранкинг и end-to-end уведомления — не входят в MVP, пока не реализованы клиентские и API-потоки.

__Q: Какой роутинг используется?__
A: Path-параметры: /posts/:uuid, /posts/:uuid/edit. Это улучшает читаемость, тестируемость и кэширование.
